# Blur and image-drag performance investigation

## What the recording shows

A local WebKit Inspector timeline, analyzed without uploading it or extracting its screenshots, covers **9.229 seconds**. Its JavaScript profile contains 1,845 samples with **1,873.215 ms of total sample weight**.

The dominant application cost is the JavaScript blur fallback, not React rendering:

| Function / operation                            | Weighted time | Share of sampled time | Samples |
| ----------------------------------------------- | ------------: | --------------------: | ------: |
| `blurPixels`, including callees                 |  1,683.737 ms |                 89.9% |   1,650 |
| `blurAxis` and `accumulate`, combined self time |  1,670.594 ms |                 89.2% |   1,637 |
| `getImageData`, self time                       |     56.843 ms |                  3.0% |      56 |
| React `performWorkOnRoot`, including callees    |     68.870 ms |                  3.7% |      69 |

The sampled hot path is:

`DrawingCanvas → drawScene → getProtectedScene → renderSurface → applyPrivacyEffects → drawBlurPatch → blurPixels`

`drawBlurPatch` accounts for 1,748.724 ms including its callees. These figures overlap: do not add inclusive parent and child times. Sample counts are **not function invocation counts**.

There are 16 application animation-frame callbacks. Fifteen take **119.957–140.266 ms**, averaging **125.168 ms**; the remaining callback takes **0.687 ms**. The overall callback median is 122.267 ms. Thus the expensive blur work alone substantially exceeds a 16.7 ms frame budget.

Representative timeline windows, measured from the recording start:

- **1.233–1.373 s:** the first expensive application callback takes 140.266 ms.
- **5.940–6.062 s:** a callback takes 122.267 ms; 109 of its 113 timestamped samples include `blurPixels`.
- **6.631–6.759 s:** a callback takes 127.767 ms; 113 of its 118 timestamped samples include `blurPixels`.
- **7.160–7.279 s:** the last expensive callback takes 119.957 ms; 107 of its 113 timestamped samples include `blurPixels`.

## Inspector overhead matters too

The recording also enabled the Inspector's screenshot instrument. It contains 36 screenshots. All 31 rendering frames longer than 100 ms that contain **no application animation-frame callback** contain Inspector screenshot captures; those frames total **4,800.169 ms**.

For example, at **1.654–1.929 s**, a 275.232 ms frame contains two Inspector captures but only 0.329 ms of recorded JavaScript. After the last application animation-frame callback, screenshot-only frames continue through **8.144 s**, generally taking 125–132 ms each.

This is strong evidence of substantial capture/encoding overhead, but the export does not provide a separate timer proving exactly how much time each capture consumed. Do not attribute all of those frame durations to application rendering or treat this recording's apparent frame rate as an uninstrumented benchmark. Repeat comparisons with **Screenshots disabled**, using the same screenshot, zoom, blur area, and drag path.

## Implementation direction

- Keep the immutable screenshot and unchanged drawing underlay cached; moving a blur boundary should not reconstruct unrelated content.
- Reduce interactive CPU blur work with a preview-only sampling scale. Apply redactions **before** any downsampling or blur sampling.
- Keep final PNG rendering at original resolution. A lower-resolution interactive blur must never replace the export source.
- Measure image movement in documents that already contain blur, not just image-only scenes. A moved image can invalidate the protected composition and trigger the same expensive blur path.
- Verify current pointer positions, cancellation, undo/redo, source edits, layer ordering, and redaction invariance alongside timing improvements.

The implementation opts into reduced sampling only for interactive CPU blur. At the default strength of 12, it reduces each axis by four: a 672 × 472 sample becomes 168 × 118, reducing filtered pixels from 317,184 to 19,824. The scale is strength-dependent and capped at eight per axis, not a fixed global pixel budget; larger blur regions can still take longer. Native canvas filters and full-resolution export retain their existing paths.

An optional unchanged-underlay cache is limited to 8,000,000 RGBA pixels, approximately 32 MB of additional pixel storage per source image. That is not a total application-memory limit. Lens-dependent scenes and larger underlays bypass this additional cache.

## Controlled before/after check

`tests/desktop/blur-preview-performance.spec.ts` exercises the real scene renderer with a
960×640 synthetic screenshot, one inserted image, a redaction, and a 600×400 blur at strength 12. It temporarily disables native canvas filters in both browser engines to exercise the
same CPU fallback used by Linux WebKitGTK. Each movement case measures seven renders;
the reported 95th percentile is therefore the slowest sample, not a long-run latency estimate.

| Browser  | Moving object                         | Before median | After median | After p95 |
| -------- | ------------------------------------- | ------------: | -----------: | --------: |
| Chromium | Blur                                  |       37.0 ms |       9.3 ms |   10.0 ms |
| Chromium | Image, with a stationary blur present |       36.4 ms |       8.8 ms |    9.4 ms |
| WebKit   | Blur                                  |       43.0 ms |       6.0 ms |   12.0 ms |
| WebKit   | Image, with a stationary blur present |       42.0 ms |       7.0 ms |   10.0 ms |

The preview reads and processes **19,824 pixels**, versus **317,184 pixels** in the unchanged
full-resolution path: a 16× reduction for this fixture. Redacted content is sanitized before
the progressive downsample, and solid masks are reapplied after blur. Changing preview
settings does not reuse an approximate effect for export. A separate underlay-cache
regression verifies that moving only the blur reuses unchanged screenshot and image content.

The preview remains visibly blurred, with a mean RGB channel difference of **1.825/255 in
Chromium** and **1.8/255 in WebKit** along the fixture's sampled edge compared with the
full-resolution result. Changing the secret pixels beneath the redaction changes **zero
output channels** in either engine; the solid mask remains opaque black, and the sampled
pixel outside the effect remains unchanged. These checks cover this fixture, not every
possible image.

These are controlled browser-fixture results, **not a new recording of the user's document**
and not a universal frame-rate guarantee. Larger blur regions, more effects, hardware, and
source changes still affect cost. Recheck the original interaction with Inspector screenshots
disabled to assess the end-to-end improvement on the user's machine.

## Relevant Excalidraw patterns

The official source at revision `a9186480121afc16ccdec789fc533e6a9ee68c10` provides useful rendering patterns:

- Its [RAF throttle retains the latest arguments while allowing only one pending callback](https://github.com/excalidraw/excalidraw/blob/a9186480121afc16ccdec789fc533e6a9ee68c10/packages/common/src/utils.ts#L183-L224).
- Its [static canvas uses viewport dimensions and avoids unnecessary bitmap resets](https://github.com/excalidraw/excalidraw/blob/a9186480121afc16ccdec789fc533e6a9ee68c10/packages/excalidraw/components/canvases/StaticCanvas.tsx#L33-L74), while a [separate interactive canvas handles interaction rendering](https://github.com/excalidraw/excalidraw/blob/a9186480121afc16ccdec789fc533e6a9ee68c10/packages/excalidraw/components/canvases/InteractiveCanvas.tsx#L142-L205).
- Its [per-element bitmap cache uses weak keys and targeted invalidation](https://github.com/excalidraw/excalidraw/blob/a9186480121afc16ccdec789fc533e6a9ee68c10/packages/element/src/renderElement.ts#L682-L732).

These support reusing unchanged raster work and separating content from interaction overlays. They are not evidence that Excalidraw uses dirty-rectangle rendering or a GPU blur implementation, and do not replace ContextSnap's redaction-before-sampling requirements.

## Method and limitations

The analysis reads only timeline metadata and profile stacks. It does not render, save, upload, or include private screenshot pixels or source URLs. No recording is checked into the repository.

Durations use `recording.startTime` and `recording.endTime`, not the longer overview selection. Script callback durations come from timeline start/end times; profiler function times are the sum of exported sample weights. Of the 1,845 samples, **1,369 have timestamp zero**: they contribute to aggregate weights but cannot reliably be assigned to an absolute timeline window. The remaining 476 samples support the later callback correlations above. Sampling and Inspector instrumentation both affect the results.

Run this read-only summary against a local recording; it prints metadata, not screenshot data or source URLs:

```sh
node --input-type=module - /path/to/recording.json <<'JS'
import { readFileSync } from 'node:fs';
const { recording: r } = JSON.parse(readFileSync(process.argv[2], 'utf8'));
const s = r.samples[0];
const totalMs = s.durations.reduce((sum, duration) => sum + duration * 1000, 0);
console.log({ seconds: r.endTime - r.startTime, samples: s.stackTraces.length, totalMs });
for (const name of ['blurPixels', 'drawBlurPatch', 'getImageData', 'performWorkOnRoot']) {
  let samples = 0, weightedMs = 0;
  s.stackTraces.forEach((trace, i) => {
    if (trace.stackFrames.some((frame) => frame.name === name)) {
      samples++;
      weightedMs += s.durations[i] * 1000;
    }
  });
  console.log({ name, samples, weightedMs, percent: weightedMs / totalMs * 100 });
}
const callbacks = r.records.filter((record) => record.eventType === 'animation-frame-fired');
console.log('callback milliseconds', callbacks.map((record) =>
  (record.endTime - record.startTime) * 1000));
console.log('samples without timestamps', s.stackTraces.filter((trace) => !trace.timestamp).length);
JS
```
